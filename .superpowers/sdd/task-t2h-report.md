The new growth state blob and the four legacy flat keys coexist in the same `judge_mom` table
without collision:

- **Blob key**: the single constant `growth_state_v1` (crate-side `state::GROWTH_STATE_KEY`).
  The blob is a JSON-serialized `GrowthState` written/read only by `set_blob`/`get_blob`.

  `dream_last_sweep_at` (crate-side `state::LEGACY_KEY_*` constants). These are flat string
  values written by the existing `turn_persist.rs:506,507,511` and `dream.rs:79` paths.

The two namespaces are disjoint by string value: `growth_state_v1` is not equal to any of the
four legacy key names, and no legacy path ever writes a key named `growth_state_v1`. Migration
reads each legacy key exactly once (when no blob is present, via `get_legacy_kv`) and writes
only the blob thereafter (`set_blob` with `growth_state_v1`), so legacy rows are preserved
untouched -- confirmed by test 3 (`legacy_keys_are_preserved_after_migration_and_save`).

## Deviations from the brief and reasons

### 1. `pub(crate) fn` instead of `pub fn` for `load_growth_state`, `save_growth_state`, `JudgeMomStateStore::new`

**Brief §3.3** specifies `pub fn load_growth_state(...)`, `pub fn save_growth_state(...)`, and
`pub fn new(...)`.

**Implemented**: `pub(crate) fn` for all three. `pub struct SystemClock` and
`pub struct JudgeMomStateStore` remain `pub` (their fields/methods do not expose `MemoryDb`
in their signatures in a way that triggers the lint; `new` does, so `new` is `pub(crate)`).

**Reason**: `MemoryDb` is declared `pub(crate)` at
`service/agent_memory/memory_db.rs:8`. Exposing it through a `pub fn` signature triggers the
`private_interfaces` lint (3 warnings: "type `MemoryDb` is more private than the item ...").
The brief's §6 hard requirement is "zero warning" for `cargo check`. These two requirements
conflict if `pub fn` is used.

The resolution chosen:
- The **module** stays `pub mod growth_adapter` exactly as §3.2 mandates (this is what avoids
  `dead_code` and mirrors `identity.rs`).
- The three **items that take `&MemoryDb`** are `pub(crate)`, matching the established pattern
  of `get_judge_state`/`set_judge_state` (also `pub(crate) fn` over `&MemoryDb`).
- The crate already carries `#![allow(dead_code)]` at `lib.rs:3`, so `pub(crate)` items with no
  production caller do **not** produce a `dead_code` warning (verified: zero warnings from
  `growth_adapter.rs`).

This preserves the brief's intent (warn-only entrypoints, no `dead_code`, module visible) while
satisfying the harder constraint (zero warnings). The behavior is identical: callers within
`northhing-core` (the only place that can construct a `MemoryDb`) can use these functions; the
follow-up wiring task in `turn_persist.rs` is also within this crate.
